## 1. 背景、用户与目标

### 1.1 产品定位与问题

当前仓库是“多 Agent 电商推荐与营销系统”，已提供推荐 API、四个 Agent 和两种编排入口，尚未形成能承担购物、交易、查单和售后的统一电商 Agent。现有商品来自内置样例，真实商品目录、价格、库存、购物车、订单、物流、售后和跨轮会话均未打通。文档中的完整能力与效果数字不可视为当前系统实绩。证据：`README.md`、`plan.md`、`main.py`、`agents/product_rec_agent.py`、`orchestrator/supervisor.py`。

**产品目标**是让用户在同一入口用自然语言完成电商任务，并由业务系统决定商品事实和交易状态。整体范围覆盖售前选品、购物车与结账交接、订单履约查询、售后申请；交付按版本推进，不把所有链路强塞进 MVP。商品类目由接入的商家目录决定，**不以耳机或其他样例类目作为产品边界**。MVP 的闭环止于宿主结账交接；在没有真实结账服务时，只能进行标明模拟数据的内部演示，不能宣称完成购买。

| 目标用户 | 主要任务 | 核心问题 |
| --- | --- | --- |
| 有明确需求的消费者 | 按用途、预算、规格找商品，比较后加购 | 搜索结果多、规格不统一、库存与价格可能不可靠 |
| 已选定商品的消费者 | 选择规格和数量，核对购物车，进入结账 | 商品族与 SKU 易混淆，报价和库存可能在加购前变化 |
| 已下单消费者（后续版本） | 查订单、物流，发起退换/退款 | 需要可信订单状态、政策、身份核验与审批 |
| 商品运营与客服 | 管理数据源、审查效果与失败原因 | 模型输出不能代替商品主数据和业务规则 |

### 1.2 可衡量目标

以下阈值均为**建议**，当前没有线上基线。先建立埋点和离线评测集，再由产品与业务方确认正式目标。

| 目标 | 指标定义 | 评审建议口径 |
| --- | --- | --- |
| 完成购物准备 | 购物准备完成率 = 有有效购买意图的会话中，成功得到经校验候选并完成购物车确认或结账交接的会话数 / 有效购买意图会话数 | 先建立线上基线；离线任务集建议 ≥ 85% |
| 避免错误商品与错误写入 | 已知缺货误荐数、超预算误荐数、未确认购物车变更数 | 自动化验收样例均为 0；分母为 0 的比率记“不可计算” |
| 帮助用户决策 | 候选曝光后对比率、加购率、结账交接率 | 按同一会话窗口计数，不把交接当成支付转化；线上目标待基线确认 |
| 稳定可用 | 完整购物回答 P95 延迟、事实校验失败率、Agent 降级率 | **建议**受控环境 P95 ≤ 4 秒；正式 SLO 待接入真实服务实测 |

## 4. 场景选择与版本范围

### 4.1 候选场景排序

优先级基于用户价值、当前代码复用、外部系统依赖和错误成本；成本为相对判断，工时**待确认**。

| 场景 | 用户价值 | 代码复用与关键依赖 | 成本/风险 | 结论 |
| --- | --- | --- | --- | --- |
| **跨品类选品 → 比较 → 选 SKU → 加购 → 结账交接** | 同一入口完成购物准备，产生明确业务结果 | 可复用推荐与库存编排骨架；必须新增目录、报价、购物车及宿主结账契约 | 中高；无支付，但有可逆购物车写入 | **P0 / MVP 核心旅程** |
| 首页个性化推荐 → 点击商品 | 覆盖流量大，但弱意图场景 | 可复用现有推荐 API；需真实用户行为、曝光点击闭环 | 中；冷启动与归因难 | P1 |
| 查订单 → 看物流 | 购买后高频任务 | 需真实订单、身份、物流状态；现仓无业务表 | 高；隐私及越权风险 | P2 |
| 退货/换货/退款 | 售后价值高 | 需政策、订单、物流逆向、资金接口、幂等与审批 | 很高；敏感写操作 | P3 |

**选择依据**：购物准备旅程复用现有四 Agent 的售前能力，同时引入电商 Agent 区别于单纯推荐接口的规格、购物车和确认能力；交接到宿主结账形成清晰边界。订单与售后会保留在统一意图体系和路线图中，待真实业务系统接入后逐步开放。耳机仅是 `agents/product_rec_agent.py` 的一类样例商品，不作为上线类目或 MVP 限制。

### 4.2 核心用户旅程

1. 用户说“给家里书房找一台 2000 元以内、可接笔记本的显示器”，或提出任一商家目录支持的商品需求。系统识别购物意图，提取类目、预算、用途与硬性要求；缺少搜索必需信息时一次只追问一个问题。
2. 商品发现 Agent 查真实目录，按商品族展示候选；用户可比较 2–3 款同类商品。属性缺失明确标注，不把猜测变成硬过滤。
3. 用户决定某款后选择尺寸、颜色等实际存在的 SKU 和数量。系统读取最新报价、库存、限购与可售区域；把购物车变更摘要呈给用户。
4. 用户明确确认加购。业务服务以会话身份、SKU、数量和幂等键更新购物车，再返回完整购物车；失败时不宣称成功。
5. 用户要求结账。系统刷新购物车报价与可售状态，展示商品、数量、价格及待宿主计算的费用；用户确认后，交接到商家控制的结账入口。Agent 不创建订单、不执行支付，也不宣称已购买。

MVP 支持商家目录中的多个类目，搜索与通用属性过滤跨类目；比较仅对同类目商品开启，并由类目配置定义维度。新类目接入前须完成 SKU、属性、报价和库存映射。页面由宿主前端承接或在本仓提供演示界面，具体责任**待确认**；无论如何，输入、候选卡、比较、规格、购物车确认、错误和交接状态都需验收。

## 5. 功能需求清单

P0 = MVP 必需；P1/P2/P3 对应后续版本。阈值与业务规则未有权威来源时按“建议”处理。

| ID / 模块 | 用户故事 | 触发条件与主流程 | 业务规则；输入 → 输出 | 异常处理 | 优先级与验收标准 |
| --- | --- | --- | --- | --- | --- |
| F01 统一入口与会话 | 我想用一个对话入口继续购物任务 | 创建会话、输入消息；路由购物/购物车/订单/售后意图；保存当前约束和已展示商品 | 输入：授权主体或匿名令牌、`session_id`、`turn_id`、文本。输出：意图、状态、会话约束。MVP 对未开放的订单/售后意图明确告知范围，不伪造结果；**建议**会话 24 小时过期 | 空输入提示；未知/过期会话提示新建；重复 `turn_id` 返回原结果；跨会话访问拒绝 | **P0**：同会话跨轮修改生效；无权限者不能读取购物车；“查物流”进入 `unsupported` 而非编造物流 |
| F02 需求解析与澄清 | 我希望系统理解预算、用途和必须满足的条件 | 解析本轮话语，合并历史明确条件；冲突或缺少必要条件时追问 | 输入：消息与显式筛选项。输出：`ShoppingIntent`，每字段有“用户明说/会话保留/推断”来源；明示条件优先，推断只作软偏好；类目必须映射至目录类目 | 解析失败提供可编辑条件；预算上下限冲突需修正；无支持类目告知范围 | **P0**：先说“预算 2000”再说“改为 1500”仅 1500 生效；未知功能不默认视为满足 |
| F03 商品发现 | 我想看到符合条件的在售商品 | 用类目、价格和硬条件查询目录；合并去重并做确定性过滤 | 输入：`ShoppingIntent`。输出：目录商品族与候选 SKU、目录版本。商品 ID、名称、属性和图片只能来自商家目录；不能回落 `MOCK_PRODUCTS` 冒充在售 | 无匹配结果提示可放宽哪些条件；目录失败返回不可用；不足额不填充错类目或超预算商品 | **P0**：至少覆盖受控测试目录的两个不同类目；下架、错类目、硬条件不符均不出现 |
| F04 报价与库存 | 我不想选到缺货或价格变化的商品 | 候选生成、加购前和结账交接前按 SKU 核价与查库存 | 输入：SKU、地区及用户可用价格上下文。输出：价格、币种、可售/缺货/未知、校验时间、来源。预算只按业务服务返回的有效价格判断；**建议**快照超过 60 秒重查 | 报价或库存未知不能标“可购买”；全部失败显示不可用；禁止现有编排的未验证商品回填 | **P0**：0 库存、超预算、过期及查询失败样例均不会形成可加购 SKU |
| F05 推荐排序与说明 | 我想知道哪些商品更适合我 | 硬过滤后按软偏好排序；输出最多**建议** 3 款短名单和理由 | 输入：已校验目录/价格/库存事实与用户约束。输出：排序、命中条件、取舍和事实来源；模型只能在候选 ID 内排序与表达，不得编造优惠、评价和配送 | 模型超时或无效输出时用确定性排序和中性模板；无事实的属性显示“未提供” | **P0**：未知/重复 ID 不入响应；理由能对应用户约束及目录字段；模型不可用仍能返回可信候选 |
| F06 比较与规格选择 | 我想比较商品并选对尺寸或颜色 | 选择 2–3 个同类目商品；读取类目维度；点选商品族的可售 SKU | 输入：已展示商品 ID、规格选择。输出：比较矩阵、变体与价格/库存。商品族不可直接加购；比较维度由类目配置，缺失值标“未提供” | 不同类目比较提示分组；无此规格、已下架、已缺货要求重选；SKU 不可由模型虚构 | **P0**：两类目各有独立可配置维度；商品族有变体时必须选到有效 SKU；同字段单位一致 |
| F07 购物车提案与确认 | 我想确认加购的是哪款、多少件 | 用户提出加购；系统展示 SKU、规格、单价、数量及校验时间；用户确认后写入 | 输入：已见 SKU、正整数数量、`action_id`、幂等键和确认决定。输出：完整购物车。写入端按会话/身份、SKU、实时库存与限购做原子校验；加购为明确用户确认后的操作 | 未确认/拒绝不写入；超量、并发库存变化、重复请求返回真实业务状态；不可用 SKU 不加入 | **P0**：未确认时车不变；重复确认只加一次；库存不足时无部分成功且给出可重试建议 |
| F08 购物车查看与修改 | 我想确认购物车并调整数量 | 查看购物车；用户要求修改或删除时生成操作摘要并确认 | 输入：购物车行 ID、目标数量或删除意图、确认与幂等键。输出：完整车、各行状态和小计；价格变化须重新提示，不沿用旧单价 | 非本会话行拒绝；库存或限购不满足时保持原车；多端并发冲突返回新版本让用户重试 | **P0**：增减/删除后的车与服务端结果一致；拒绝或失败没有隐式写入 |
| F09 结账交接 | 我想核对商品后去商家结账 | 用户提出结账；重查价格与库存；展示摘要；用户确认交接 | 输入：购物车版本、确认决定。输出：宿主提供的受控 `checkout_url` 或宿主路由标识，状态只能是“已交接”。运费、优惠、税费若无数据源则标“待结账页确认”；Agent 不创建订单、不扣款 | 价格/库存变化阻止旧摘要交接并重确认；无有效宿主入口显示不可用；非法 URL 拒绝 | **P0**：变化后需新确认；交接只到白名单宿主；响应从不出现“支付成功/订单已创建” |
| F10 页面与反馈 | 我想看清结果和错误 | 展示输入、候选、比较、SKU、确认单、购物车和交接卡；卡片实际可见时记曝光 | 输入：响应状态和用户操作。输出：可操作 UI 与曝光、比较、加购、交接事件；错误有重试或调整条件入口 | 部分失败明确标识；重复事件去重；事件采集失败不阻断购物 | **P0**：正常、空结果、缺货、价格变化、模型降级、写入失败、交接完成七种状态可见；同事件只计一次 |
| F11 授权个性化与实验 | 我希望系统理解已授权偏好，运营能测不同策略 | 数据源与埋点稳定后读取行为；稳定分桶并应用不同策略 | 输入：授权行为、实验配置。输出：软偏好和实验版本；硬条件始终以本轮输入优先 | 无授权或配置失效回退当前会话/控制组 | **P1**：撤回授权后无历史画像；不同实验组实际调用不同配置 |
| F12 订单与物流 | 我想查自己的订单和当前配送状态 | 识别查单意图；验证身份；查询本人订单、物流事件并组织答复 | 输入：授权身份、订单 ID/用户选择。输出：订单状态、最后事件、来源时间；不得从聊天历史推断配送 | 无订单、非本人订单、物流接口失败分开处理 | **P2**：越权订单不可见；回答与订单及物流事件一致 |
| F13 售后申请 | 我想了解退货资格并提交申请 | 验证身份和订单；读取现行政策；计算资格与退款金额；展示方案；用户确认，必要时人工审批 | 输入：订单行、原因、政策版本、确认/审批。输出：资格、申请状态、审计记录；规则由业务服务执行 | 不符合政策说明原因；重复申请幂等；审批拒绝无退款动作 | **P3**：无确认/审批时状态不变；跨用户、重复申请及并发冲突有确定结果 |

### 5.1 建议接口契约

新增 `/api/v1/commerce` 命名空间承载购物旅程，避免把现有 `RecommendationRequest.context` 任意字典当成交易协议。路径可在接口评审调整，字段与状态语义要固定。

| 方法与建议路径 | 请求关键字段 | 响应关键字段 |
| --- | --- | --- |
| `POST /api/v1/commerce/sessions` | 宿主身份或匿名令牌 | `session_id`、`expires_at` |
| `POST /api/v1/commerce/sessions/{id}/turns` | `turn_id`、`message`、显式筛选 | `request_id`、`intent`、`status`、`constraints`、`items[]`、`question`、`proposed_action` |
| `POST /api/v1/commerce/sessions/{id}/compare` | 2–3 个已展示商品 ID | `dimensions[]`、`products[]`、`differences[]` |
| `POST /api/v1/commerce/sessions/{id}/actions/{action_id}/confirm` | `approved`、`idempotency_key` | `status`、`cart`、`error_code` |
| `GET /api/v1/commerce/sessions/{id}/cart` | 会话所有权令牌 | `cart_id`、`version`、`items[]`、`subtotal` |
| `POST /api/v1/commerce/sessions/{id}/checkout-handoff` | 购物车版本、用户确认 | `status=handoff`、受控 URL/宿主路由、最新摘要 |
| `POST /api/v1/commerce/events` | `event_id`、`request_id`、会话及事件类型 | 接收/去重结果 |

对话状态**建议**采用 `clarify`、`shortlist`、`compare`、`confirm_action`、`cart_updated`、`handoff`、`unsupported`、`unavailable`。不能用 `handoff` 代表下单或支付成功。

## 6. Agent 协作、工具与审批

| Agent / 组件 | 职责与数据来源 | 工具边界 |
| --- | --- | --- |
| 新增意图与需求解析 Agent | 识别购物、购物车、查单、售后意图；从消息和会话抽取结构化约束 | LLM 只生成受 schema 限制的提案；MVP 未开放意图返回 `unsupported`；不得猜测身份或政策 |
| 现有用户画像 Agent（调整） | 在授权且真实特征源接入后提供软偏好；MVP 主要使用用户本轮显式约束 | `services/feature_store.py`；不能把现有硬编码浏览/购买样例当真实用户数据 |
| 现有商品推荐 Agent（调整） | 搜索目录、取同一候选集并排序，结合已核实商品事实给出 ID | 目录搜索/详情与可选向量召回；不得生成目录外 SKU 或决定硬性价格库存 |
| 现有库存 Agent（调整） | 批量获取 SKU 可售状态、更新时间与错误 | 商家库存/MySQL 适配器；不使用 `Product.stock` 样例值作实时库存 |
| 现有营销文案 Agent（调整） | 生成中性推荐理由和比较取舍 | 仅用目录规格、报价和用户明确需求；无事实来源时不用优惠、历史最低价、销量、评价、配送承诺 |
| 新增购物车执行组件（确定性服务） | 读车、生成变更摘要、确认后执行写入、检查版本/数量/库存/幂等 | 商家购物车后端；Agent 只能提出动作，业务服务与用户确认决定是否写入 |
| Supervisor | 编排意图、目录、报价、库存、推荐与购物车状态；统一响应、日志和降级 | 硬过滤、权限、外链和写入门禁由代码执行。`orchestrator/supervisor.py` 与 `orchestrator/graph.py` 如共同上线必须复用业务服务 |

**MVP 编排**：消息 → 意图/约束 → 目录搜索 → 报价与库存并行核验 → 硬条件过滤 → 排序与理由 → 对比/规格选择 → 购物车动作提案 → 用户确认 → 原子写车 → 重新核价 → 用户确认 → 宿主结账交接。购物车写入前后的状态必须从业务服务读取，不能由对话文本推断。比较及购物车操作复用同一已展示商品溯源集。参考 `ecommerce-agent-references/commerce-agents/shopping-agent/core/shopping_agent/gates.py`。

**确认和人工审批**：搜索、比较、查本人订单是只读操作；加购/改数量/删除及结账交接必须由用户在可见摘要上明确确认。用户拒绝时不写入。结账交接不执行支付。未来取消订单、退货、换货需要身份核验与明确确认；退款等资金动作是否需要人工审批、额度与角色由商家政策**待确认**，技术实现可参考 `ecommerce-agent-references/HelpPilot/helppilot/graph.py` 的可恢复审批，但本仓尚未实现。

## 7. 数据模型与外部依赖

| 对象（建议） | 最小字段与规则 | 数据来源 |
| --- | --- | --- |
| `CommerceSession` / `ShoppingIntent` | `session_id`、主体、过期时间、当前意图、类目、预算、用途、硬/软条件及字段来源、已展示商品 ID、会话版本 | 宿主身份/匿名令牌与会话存储；**建议** Redis 短期保存，隔离不同主体 |
| `CatalogProduct` / `SKU` | 商品族 ID、SKU ID、类目、名称、品牌、类目属性、变体选项、图片、授权详情 URL、上下架状态、目录版本 | 商家目录；商品族不能直接加购。参考 `ecommerce-agent-references/commerce-agents/shopping-agent/core/shopping_agent/types.py` |
| `OfferSnapshot` / `AvailabilitySnapshot` | SKU、`Decimal` 价格、币种、地区、可售状态（可售/缺货/未知）、校验时间、来源版本 | 报价/库存业务服务；未知状态与缺货分开，均不作为可加购商品 |
| `Cart` / `CartLine` | 购物车 ID、主体、版本、SKU、规格快照、数量、当前单价、行金额、小计、更新时间 | 商家购物车服务；小计由后端计算，优惠/运费/税费需独立权威数据 |
| `PendingAction` / `CheckoutHandoff` | 动作 ID、类型、目标购物车版本、商品与数量、确认状态、幂等键；交接入口与失效时间 | 服务端保存；交接入口由宿主生成，模型不能生成 URL |
| `CommerceEvent` | 事件 ID、请求/会话 ID、意图、商品/SKU、状态、数据版本、时间、失败原因 | 可去重分析与审计存储，不把原始聊天全文放进公共指标 |
| `Order` / `AfterSalesCase`（后续） | 所有人、订单行、状态事件、金额与政策版本、申请及审批状态 | 真实订单、物流、资金与售后系统；MVP 不造订单 |

**MVP 外部依赖**：商家商品目录、报价/库存、购物车服务、宿主结账交接及身份/匿名会话机制。当前 `infrastructure/redis_client.py`、`infrastructure/mysql_client.py`、`infrastructure/milvus_client.py` 只提供连接，不提供这些业务表与接口。没有接入条件时可用明确标为模拟的测试桩评审交互，但不得对外宣称真实可购买。Milvus 语义召回和历史用户画像可在 V1 结合目录规模和指标验证后引入。

## 8. 非功能需求、关键指标与风险

| 维度 | MVP 要求 / 建议 | 验证 |
| --- | --- | --- |
| 数据可信 | 商品事实、报价、库存、车状态均有来源版本与时间；**建议**价格/库存快照超过 60 秒重查；未知不能标可买 | 注入下架、涨价、缺货、超时、过期；响应及购物车不使用旧事实 |
| 安全与隐私 | 会话与购物车绑定宿主身份或匿名令牌；确认动作附幂等键和版本；交接 URL 白名单；限制输入与速率 | 越权访问、重复确认、并发修改、恶意 URL、超长输入测试；关注 `main.py` 当前宽松 CORS 与未鉴权实验写接口 |
| 可靠性 | 模型不可用时可用确定性排序/模板；目录、报价、库存或购物车失败时返回明确状态，禁止假成功 | 故障注入后无伪造候选、车更新或订单确认 |
| 性能 | **建议**完整购物回答 P95 ≤ 4 秒；写车与交接另测 P95/P99，正式 SLO 待业务系统实测 | 记录解析、检索、报价库存、排序、购物车各阶段时延 |
| 内容质量 | 理由及对比映射真实属性；促销主张在无事实源前禁用；结账交接文案不称“已购买” | 离线评测集与人工抽检 |
| 可观测性 | `request_id` 贯穿 Agent 与工具；记录失败类型、降级、空结果、确认/拒绝和业务状态 | 指标可按意图、类目、数据源、版本聚合；`services/metrics.py` 现有进程内指标不够 |

看板按会话计算：有效购物会话数、合格候选率、空结果率、已知缺货/超预算误荐数、比较率、确认加购率、购物车写入失败率、结账交接率、撤回/拒绝率、各阶段 P50/P95/P99。曝光只在卡片实际可见时上报；交接不计入订单或支付转化。

| 主要风险 | 处理与上线门槛 |
| --- | --- |
| 真实目录、报价、库存、购物车/结账宿主尚不存在于本仓 | 确认服务负责人、接口、测试环境和授权；缺任一关键源时仅内部模拟演示 |
| 当前推荐过滤后回填未校验商品 | 在 `orchestrator/supervisor.py`、`orchestrator/graph.py` 改为严格空结果/不可用；加入回归样例 |
| 商品族、SKU 和多类目属性差异 | 建 SKU 契约和类目维度配置；未映射规格不可加购或作确定性比较 |
| LLM 越权写车或编造价格/优惠 | 写操作只接受已见 SKU、用户确认和服务端校验；表达只用已核实事实 |
| 购物车并发与重复请求 | 后端原子库存/限购校验、购物车版本与幂等键；进程内锁不能代替后端约束 |
| 文档效果数字与实际能力不一致 | `README.md`、`plan.md` 中的示意数字不作基线；以上线埋点和评测为准 |

**待确认**：① 商品、SKU、报价、库存、购物车和结账服务各由谁提供，支持哪些类目与地区？② 宿主是否支持匿名购物车、变体选择和结账交接，前端在哪个仓库交付？③ 限购、价格有效期、优惠/运费展示规则和交接 URL 时效是什么？④ 查单及售后版本的身份验证、退货政策、退款审批角色与额度是什么？⑤ 产品指标、SLO 与试点人群如何定基线？

## 9. MVP 与后续版本及端到端验收

| 版本 | 交付范围 | 出口标准 |
| --- | --- | --- |
| **MVP / P0** | 统一购物入口、跨目录类目选品、比较与 SKU 选择、实时核价查库存、确认加购/改车、结账交接、埋点与降级 | 第 9 节场景通过；真实业务接口对外可用，否则仅标明模拟的内部演示 |
| V1 / P1 | 授权个性化、首页推荐、多类目属性配置扩展、检索/文案实验、持久化分析 | 有目录覆盖、行为授权、曝光点击基线，实验策略实际生效 |
| V2 / P2 | 本人订单查询、物流事件与异常解释 | 身份、订单、物流系统联通且权限/状态测试通过 |
| V3 / P3 | 退换/退款申请、政策检索、可恢复人工审批 | 真实政策与资金/售后系统联通；审计、幂等和审批验证通过 |

端到端测试用受控目录、报价、库存、购物车和宿主交接桩构造确定性场景；对外发布前须以真实测试环境复跑。现有 9 个测试不能替代这些验收。

| 场景 | Given / When | Then |
| --- | --- | --- |
| 跨品类购物 | 目录包含显示器和键盘；用户分别提出“2000 元内能接笔记本的显示器”和“无线键盘” | 两次均检索对应真实类目；预算、属性过滤正确；不靠耳机内置样例补数 |
| 比较与 SKU | 同类两款显示器可比较，一款有不同尺寸 SKU；用户选择 27 英寸 | 比较维度一致，缺失参数标明未知；购物车提案使用已见、可售的 27 英寸 SKU |
| 价格库存与确认 | 候选 A 有货且 1800 元，B 缺货，C 为 2200 元；用户预算 2000，确认加购 A 1 件 | B/C 不作为可加购候选；确认前车不变，确认后只增加 A 一件；返回完整购物车 |
| 价格变化与交接 | 加购后 A 涨价或缺货；用户要求结账 | 展示新事实并要求重新确认或移除商品；旧摘要不能交接；成功交接仅显示“前往商家结账”，无订单/支付成功声明 |
| 幂等与越权 | 同一动作确认发两次，或另一会话尝试读/改购物车 | 只写入一次；另一会话被拒绝，车状态不泄露 |
| 故障与模型越界 | 报价超时、库存未知，或模型返回目录外 SKU/虚构优惠 | 不把无效商品加购；返回明确不可用/降级状态；无虚构优惠和假成功 |
| 范围提示 | 用户问“我的订单到哪了”或“帮我退款” | MVP 明确当前未接通订单/售后并引导到既有宿主渠道；不编造订单状态、不提交退款 |
